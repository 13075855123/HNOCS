## 一、系统概述

### 1.1 架构总览

**Task-driven 光电混合片上网络仿真器**。4×4 Mesh 拓扑，16 个 TaskPE + 16 个 5 端口光路由器 + 1 个 GlobalBuffer。

控制面走电路由器（电层握手），数据面走光波导（sendDirect 直传）。每条光电路先经 SETUP_REQ→SETUP_ACK 电层握手分配波长，再通过光旁路直传全部数据 flits，END_FLIT 触发拆链和波长释放。

```
控制面（电）:  setup_req → 电 router → setup_ack
数据面（光）:  START_FLIT → sendDirect → ... → END_FLIT → teardown
热调谐（基线）: 160 微环/路由器 × 2mW/环 → 320mW/路由器 → 全芯片最坏 5.12W
SOA（逐跳）:   每路由器输出端口后 SOA × 80mW/器件 → 按电路持续时间累计能耗
激光器（片外）: CW 常亮, P_elec = 1mW / 0.20 = 5mW, 不计入芯片热模型
```

### 1.2 关键设计决策

- **电层基线保守化**：PE 功耗、热阻参数取成熟 CMOS 工艺保守值（非先进节点），确保与光层的对比区分度
- **光层参数物理一致性**：C++ 与 Python 器件参数统一对齐，SOA 增益下调至 10 dB 避免逐跳过饱和，接收灵敏度上调至 -12 dBm 符合 256G PAM4 现实值
- **周期性 DVFS**：每 100ns 重检 PE 温度并调整计算推进速率，替代原一次性 DVFS 方案
- **CCR 谱系 Benchmark**：5 个任务图覆盖 CCR 0.06→8 全范围，系统评估光层在不同计算/通信比下的收益

## 三、光路由器微环架构

5 端口 microring-based 光路由器。端口定义：**0=Local, 1=West, 2=North, 3=East, 4=South**。

物理实现为 waveguide crossing 交叉杆拓扑：5×5 交叉点，排除 5 个自路由对角，**有效交叉点 20 个**。每个交叉点串联 8 个微环谐振器（每 WDM 波长一个）。

> **20 交叉点 × 8 波长 = 160 微环/路由器。全芯片 16 × 160 = 2560 个微环。**

各方向路径的 through-count 公式（n=8 波长, i 为波长索引 1..8），每路径额外 dropCount=1：

| 方向组 | 公式类型 | through 范围 | 最长 (i=8) |
|--------|:---:|------|:---:|
| L→W, W→S, N→L, E→N | Type 0: i−1 | 0–7 | 8 |
| L→S, N→W, E→L, S→E | Type 1: 2n+i−1 | 16–23 | 24 |
| L→N, L→E, W→L, S→L | Type 2: 3n+i−1 | 24–31 | 32 |
| W→E, N→S, E→W, S→N | Type 3: 4n | 32 | 33 |
| W→N, E→S | Type 4: 4n+i−1 | 32–39 | 40 |
| N→E, S→W | Type 5: 6n+i−1 | 48–55 | **56** |

### 4.3 光传输时序

```
Task 计算完成
  → sendTaskData(): 创建全部 flits, 放入 pendingDataQ[dst]
  → tryReserveSetupPath(): XY 路径预留 2 个波长
  → 电层路由发送 SETUP_REQ
  → 等待 SETUP_ACK (超时 200ns, 重试间隔 50ns)

SETUP_ACK 到达
  → circuitReadyByDst[dst] = 1
  → flushPendingData(): 全部 flits → opticalDataQ
  → sendOpticalFlitFromQ(): 逐个 flit sendDirect (START → ... → END)

END_FLIT 发出
  → releaseOpticalPathByToken() 释放波长
  → SOA 电能耗累计: soaCount × 80mW × 持续时间
  → 动态调谐能耗累计: 移除各路由器热调谐功率, 累计 Σ tuningPower × duration
  → circuitReadyByDst[dst] = 0
```

**动态热调谐时序**:
```
SETUP_ACK 到达
  → getDeviceLevelPathMetrics() 构建全路径器件链
  → 各路由器独立计算调谐功率（不依赖 budget 汇总值）:
      从 pathEdges 推导每跳 (dx,dy) → 端口映射 → 查 routerTurnMatrices
        → formulaType → throughCount = evalFormula(maxWl, totalWL)
        → ringCount_i = throughCount + numActiveWL (路由器转向)
        → 源 NI: ringCount_i += maxWl (调制器共享链)
        → 目的 NI: ringCount_i += maxWl (解调器共享链)
      P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
  → addRouterOpticalPower(routerId, P_i) 注入热模型
  → SOA 功率: 每跳前一个路由器出端有一个 SOA
      → routers[0..N-2] 各得 opticalSoaPumpPower_mW (dstId 无 SOA)

END_FLIT 发出
  → removeRouterOpticalPower() 逐路由器移除
  → totalDynamicTuningEnergy_J += Σ tuningPower × circuitDuration
  → totalSoaEnergy_J += soaCount × 80mW × circuitDuration
```

**光层每 flit 传输时间**: 16B × 8 / 256Gbps = **0.5 ns**
**电层每 flit 传输时间**: 16B × 8 / 16Gbps = **8 ns**

### 4.4 预算模型路径构建修复 (2026-05-30)

端口映射修正为统一逻辑约定 (0=Local, 1=West, 2=North, 3=East, 4=South)。修复内容包括:

| 问题 | 修复前 | 修复后 |
|------|--------|--------|
| 南向 (dy=+1) 端口 | N→L (inP=2, outP=0) | N→S (inP=2, outP=4) |
| 北向 (dy=-1) 端口 | L→N (inP=0, outP=2) | S→N (inP=4, outP=2) |
| 目的路由器转向 | **缺失** | 新增 direction→Local(0) egress turn |
| deviceIndex 编码 | 不一致 | 统一 `nodeId×1000 + inPort×100 + outPort×10 + subIdx` |

2026-05-31 验证结果：10/10 单元测试通过，覆盖 4 方向 × 3 角色端口映射、20 port pair 合法性、单跳/自环边界、SNR=38.6dB 预算合理性、deviceIndex 编码一致性。

### 4.5 Per-Router 独立调谐计算 (2026-05-31, 2026-06-01 修正)

旧方案：budget 函数计算 `totalTuningPower_mW`，随后在 `tryAllocateOpticalPathForPacket` 中按各路由器 ΔT 比例分配 → 近似值，与底层逐环计算不完全一致。

新方案：**各路由器独立查询自身温度，直接计算自己的调谐功率**，不依赖 budget 的汇总值。

```
for each router i on the path:
    1. 从 pathEdges 推导 (dx, dy) → 方向端口映射:
       - 源路由器: inPort=0(Core), outPort=direction
       - 中间路由器: inPort=来向反方向, outPort=去向
       - 目的路由器: inPort=来向反方向, outPort=0(Core)

    2. 查 routerTurnMatrices[inPort][outPort] → formulaType → throughCount:
       - Type 0: maxWl-1
       - Type 1: 2n + maxWl - 1
       - Type 2: 3n + maxWl - 1
       - Type 3: 4n
       - Type 4: 4n + maxWl - 1
       - Type 5: 6n + maxWl - 1

    3. ringCount_i = throughCount + numActiveWL           (路由器转向)
       if (i == 0) ringCount_i += maxWl                   (源 NI 调制器共享链)
       if (i == numRouters-1) ringCount_i += maxWl        (目的 NI 解调器共享链)

    4. P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
```

> **2026-06-01 修正**：NI 调制器/解调器的微环数从 `numActiveWL` 改为 `maxWl`。NI 是一条共享总线上的 ring 1..maxWl 链，活跃波长位置的环为 DROP，非活跃波长位置为 THROUGH。总计 `maxWl` 个不同物理微环（不是 `numActiveWL` 个，也不是 per-λ 重复计数的 `Σ wl_i` 个）。

### 4.6 SOA 功率精确归属 (2026-05-31)

旧方案：SOA 总功率均摊到路径所有路由器（含 dstId）→ 物理不准确。

新方案：每个 SOA 位于前一跳路由器的输出端，功率归属到驱动路由器。

```
SOA 归属: routers[0..N-2] 各得 opticalSoaPumpPower_mW (80mW)
          routers[N-1] (dstId) = 0  (不驱动任何输出)
总 SOA 功率: 80mW × pathEdges.size() (不变)
```

### 4.7 NI 调制/解调器共享链模型 (2026-06-01)

旧方案：预算模型 `getDeviceLevelPathMetrics` 中，对每个波长独立调用 `buildModulatorSegments` / `buildDemodulatorSegments`，每个波长生成 `(wl-1) through + 1 drop` 微环。多波长时 through 微环被重复生成（如 λ₃ 和 λ₅ 各自生成 ring 1 和 ring 2），在 `computeDeviceLevelBudget` 中被重复计入热调谐功耗。

新方案：共享链模型。ring 1..maxWl 只生成一次，活跃波长位置为 DROP，其余为 THROUGH：

```
Source NI:
  for r = 1..maxWl:
    if r in activeWavelengths → DEV_RING_DROP
    else → DEV_RING_THROUGH
  // 总计 maxWl 个不同物理微环，无重复

Destination NI:
  for r = 1..maxWl:
    if r in activeWavelengths → DEV_RING_DROP
    else → DEV_RING_THROUGH
  // 每个活跃波长独立 waveguide → PD
```

Per-Router 调谐计算中 NI 微环数也同步改为 `maxWl`（见 4.5）。

### 4.8 目的路由器 deviceIndex 编码一致性 (2026-06-01)

目的路由器 egress turn（direction→Local）的 deviceIndex 显式加入 `dstOutPort * 10` 项（outPort=0），与中间路由器编码格式统一为 `nodeId × 1000 + inPort × 100 + outPort × 10 + subIdx`。功能上等价（0*10=0），但保证编码一致性。

## 五、波长分配

### 5.1 分配流程

1. `buildXYPathEdges()` — 构建 XY 维序路由边列表
2. 遍历 2 个 spatial channel，对每个 channel 收集所有空闲波长
3. 策略 `"lowest"`: 取前 `opticalRequiredWavelengths` (2) 个最低索引空闲波长
4. 占用: `edgeOccupancy[spatial][wlIdx] = pktId`
5. 预计算设备级光链路预算并缓存
6. 若所有 spatial channel 均不足 → 返回失败，PE 进入重试循环

### 5.2 数据结构

```
opticalEdgeOccupancy: map<edgeKey, [numSpatialChannels][maxWavelengths]>
  — 每条无向边的 (spatial, wavelength) 占用矩阵

opticalPacketAllocations: map<pktId, OpticalPacketAllocation>
  — 每条活跃光路的完整信息, 含:
      pathRouters, tuningPowerPerRouter_mW(vector), soaPowerPerRouter_mW(vector),
      setupTime (用于 SOA 能耗 + 动态调谐能耗计算)

OpticalDevicePath::perRouterTuningPower_mW: map<routerId, power_mW>
  — computeDeviceLevelBudget 按 deviceIndex/1000 分组累加
  — 可用于与 per-router 独立计算交叉验证
  — 通过 OpticalPathMetrics::perRouterTuningPower_mW 对外暴露
```

### 5.3 边容量

```
每边槽位 = 8λ × 2 spatial = 16
每电路占用 = 2λ
每边最大并发 = 8 条电路
```

## 六、CCR 与 Benchmark 设计

### 6.1 CCR 定义

**CCR (Compute-to-Communication Ratio)** 衡量任务的计算密集度：

```
CCR = computeTime_ns / (numFlits × 8 ns)
```

- CCR < 1：通信主导，光层 256Gbps 带宽优势显著
- CCR ≈ 1：平衡，光层有加速但需考虑能耗代价
- CCR > 1：计算主导，传输时间被计算掩埋

### 6.2 五个 Benchmark 设计

设计原则：形成 CCR 从 0.06 到 8 的谱系，系统评估光层在不同工作负载下的表现。

| Benchmark | 角色 | 目标 CCR | 计算 (ns) | 数据量 (B) | 最大 flits |
|---|---|---|---|---|---|
| **Optic** | 极端通信密集 | ~0.06 | 1,000 | 4K–32K | 2,048 |
| **VOPD** | 通信为主 | ~0.3 | 7K–10K | 6K–96K | 6,000 |
| **MPEG4** | 平衡型 | ~1 | 10K–25K | 4K–64K | 4,000 |
| **HNN** | 计算倾向 | ~3 | 20K–50K | 8K–32K | 2,048 |
| **GEMM** | 极端计算密集 | ~8 | 15K–50K | 1K–8K | 512 |

**Optic**: 16 PE→4 GB 端口，全并发回传，通信压力最大。
**VOPD**: 13 tasks pipeline，大数据级间传递。
**MPEG4**: 12 tasks，中等计算和通信混合。
**HNN**: 32 tasks 深度 4 级流水线，16 PE 并行 Stage 3，重度计算。
**GEMM**: 11 tasks 矩阵乘归约树，计算 dominate。

### 7.5 关键发现

1. **CCR < 1（Optic、VOPD）：光层完胜**。时间缩短 4-6×，能耗降低 49-59%。大数据量摊平光电路 setup 开销，256Gbps vs 16Gbps 带宽优势主导。

2. **CCR ≈ 1（MPEG4）：转折点/接近盈亏平衡**。时间缩短 1.87×，光层总能耗仅比电层高 2.3%（接近测量误差范围）。MPEG4 作为转折 benchmark 表明 CCR≈1 是光电混合 NoC 能耗优势的临界区域——通信继续增加（CCR 下降）则光层有利，计算继续增加（CCR 上升）则电层更优。

3. **CCR > 3（HNN、GEMM）：光层得不偿失**。时间几乎无差（1.14-1.34×），因为计算主导了总延迟。Ring tuning 能耗是纯负担，总能耗反超 18-35%。

4. **Ring tuning 是光层能耗的主要挑战**：全芯片 2560 个微环在最坏情况（全部需要热锁定）下总基线功耗达 5.12W。实际应用中可通过仅锁定活跃环、动态电源门控等方式降低开销。动态按需调谐方案将调谐功耗从"通信无关的固定开销"转变为"与通信负载成比例的可变开销"，TuningRatio < 0.05%。

5. **CCR 是预测光层收益的可靠指标**：文献中光 NoC 研究的共识是存在"盈亏平衡消息大小"（break-even message size）——消息必须足够大才能摊平电路建立开销。CCR 将该直觉量化为可计算指标，使论文可用 CCR 梯度论证"光电混合 NoC 应依据工作负载的通信密集度来决定是否启用光旁路"。

#### 7.9.3 温度↔调谐耦合与仿真时间尺度

调谐功率公式：
```
P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
     = ringCount_i × 0.05 mW/K
```

**T → P_tuning（温度影响调谐）——线性显著**：
- ΔT=0K: P_i = 0（无需调谐）
- ΔT=10K: 最坏路径（56 环）P = 56 × 0.5 = 28 mW/路由器
- ΔT=20K: P = 56 × 1.0 = 56 mW/路由器

**P_tuning → T（调谐影响温度）——可忽略**：
- 热时间常数 τ = R_conv × C_router = 10 K/W × 10⁻⁷ J/K = **1 μs**
- 实测动态调谐全芯片平均功率 < 3 mW，在 200 μs 仿真中累积能量 < 6×10⁻⁷ J
- 此热量可产生的路由器温升 < 0.01K，对 DVFS 节流无影响

**仿真时间尺度的局限**：
- μs 级仿真中，路由器温度由 SOA（80 mW/跳 × 低占空比 ~5%）主导，ΔT < 1K
- Thermal ON vs OFF 对比实验（7.8 节）证实：热调谐在 μs 尺度不影响仿真时序
- **但在真实系统稳态运行中，PE 计算功耗（2.5W × 16 = 40W，经 R_pe2router=3 K/W 耦合）会将路由器加热到 ΔT=10-20K，此时调谐功率不可忽略**

#### 7.9.4 稳态调谐功耗投影

基于 RC 热模型稳态求解（PE 全负荷 @ 2.5W, T_ambient=318.15K）：

| 场景 | 路由器 ΔT | 活跃环数（全芯片） | 调谐功率 | vs 静态基线 (5.12W) | 占芯片总功耗 |
|------|:--:|:--:|------|:--:|:--:|
| 冷启动（μs 级） | ~0.5K | ~500 | ~1.3 mW | 0.025% | < 0.01% |
| 稳态运行 | ~10K | ~800 | ~400 mW | 7.8% | ~1% |
| 稳态 + 热点 | ~20K | ~1200 | ~1.2 W | 23% | ~3% |
| 最坏（全部活跃+热点） | ~30K | ~1500 | ~2.25 W | 44% | ~5.5% |
| 静态基线（全常开） | — | 2560 | 5.12 W | 100% | ~13% |

> 稳态 ΔT 的主要来源是 **PE 计算功耗通过 R_pe2router 热耦合加热路由器**，而非 SOA 或调谐自身。调谐功耗是温度变化的"消费者"而非"生产者"。

**核心结论**：即使在稳态最坏情况下，动态调谐功耗（~1.2W）仍比静态基线（5.12W）低约 4 倍。μs 级仿真因为路由器温度尚未偏离 T_ambient 而低估了调谐能耗，但按稳态投影修正后，动态调谐的优势性质不变。

#### 7.9.5 论文论述建议

**论点 1：动态按需调谐是光电混合 NoC 的使能技术。**
若所有 2560 个微环常开（静态 5.12W），光层能耗优势（相对于电层）将在 CCR>1 的场景中完全丧失。动态调谐即使在稳态热点下也能将调谐功耗控制在 1-2W 以内（节省 4-200×），是实现光 NoC 能耗收益的前提。

**论点 2：温度感知是必要的，但热反馈是单向的。**
调谐功率随 |T| 线性增长，忽略温度效应会低估热点场景下的调谐开销（可能低估 10-100×）。但调谐功耗本身不足以显著加热芯片（P_tuning ≪ P_PE），耦合是单向的。Per-Router 独立查询温度是合理的工程实现。

**论点 3：仿真时间尺度需要与热时间常数匹配。**
μs 级仿真的热调谐能耗不代表稳态运行。论文应明确区分"瞬态仿真验证了调谐机制的工程正确性"与"稳态投影评估了调谐的实际能耗量级"，建议增加稳态分析模型补充 μs 级仿真的不足。

| **论点 4：SOA 而非微环调谐是光层动态功耗的主导。**
SOA 逐跳放大功耗（80 mW/跳 × 活跃跳数）在所有 benchmark 中均超过调谐功耗 1-3 个数量级，是光层动态功耗的首要优化目标。

**论点 5：光收发器能耗取 40 pJ/flit（25+15），为电层（300 pJ/flit）的 13%。**
当前值对应 28nm CMOS 工艺节点的 microring 调制器驱动（~200 fJ/bit）和 PD+TIA+CDR 接收链路（~30mW @ 256Gbps PAM4）。即使数据包增大 2 倍（如 Optic 32KB→64KB，flit 2048→4096），光收发器总能耗仍不到电层的 1/7。但若采用 45nm 成熟工艺，应上调至 60-90 pJ/flit，论文需标注工艺节点假设。

| 参数 | 本文值 | 影响 | 评估 |

**关键发现**：

1. **PE 热时间常数 τ_pe = R×C = 8×1e-6 = 8 μs**。HNN 实测 PE 温度最高 55.5°C（超出 T_throttle=54°C），DVFS 对重度计算 PE 产生 9-12% 减速。PE 热效应是仿真中唯一显著的温控机制。

2. **C_pe/C_router 仅建模有源层**（~10μm 厚），忽略体硅衬底（~500μm）的蓄热能力。这导致 τ 偏小（8 μs vs 全芯片 ~500 μs），PE 升温偏快。在 μs 级仿真中影响不大，但在 ms 级以上仿真中会导致温度响应过快。

3. **光收发器能耗已修正为 40 pJ/flit（调制器 25 + 接收器 15），对应 28nm CMOS 节点**。光收发器为电收发器（300 pJ/flit）的 13%（即光:电=1:7.5），加上 16× 带宽优势，光层在 per-flit 传输能耗和时间两个维度均显著优于电层。若数据包增大 2 倍（如 Optic 32KB→64KB，2048→4096 flit），光收发器能耗从 1.31 μJ 增至 2.62 μJ，电收发器从 9.91 μJ 增至 19.8 μJ，光/电比不变（1:7.5），定性结论不变。

4. **T_throttle=54°C 较激进**。商用芯片通常节流点在 80-90°C。较低的节流点使 DVFS 更早触发，夸大了热管理挑战。建议论文中标注这是"保守热管理策略"。

5. **仿真时间尺度是根本局限**。10-205 μs 不足以让芯片达到热稳态。当前结果代表"冷启动"瞬态行为，真实系统稳态（ms 级以上）的调谐功耗和 DVFS 行为会显著不同。建议在论文中增加稳态分析或解析模型投影。

> **核心结论**：当前参数集整体合理，主要偏差在于光收发器能耗（偏乐观 10×）和 T_throttle（偏保守）。μs 级仿真无法捕捉全芯片热稳态，论文应明确区分"瞬态仿真验证机制"和"稳态投影评估量级"。

### 7.10 CCR 取值的严谨性分析 (2026-06-02)

#### 7.10.1 CCR 不是 Benchmark 的固有属性

在 NoC 文献中，**CCR 没有标准化数值**。VOPD、MPEG4、HNN、GEMM 等 benchmark 的 CCR 取决于三个独立变量：

```
CCR = computeTime_ns / (dataSize / 16B × 8ns)
```

| 变量 | 含义 | 调整方式 |
|------|------|---------|
| `computeTime` | PE 计算时间 (ns) | 修改 CSV 第 3 列，代表 PE 处理速度 |
| `dataSize` | 每次通信数据量 (B) | 修改 CSV 第 4 列，代表任务间数据量 |
| `flitSize` | 微片大小 (16B) | 固定常数 |

**同一 benchmark，不同实现者会得到完全不同的 CCR**。例如 MPEG4 在不同论文中可能从 CCR≈0.5（低分辨率 + 快速 PE）到 CCR≈5（高分辨率 + 慢速 PE）不等。

#### 7.10.2 本文 CCR 梯度设计的合理性

本文的策略是：**以 CCR 为自变量，覆盖从极端通信密集到极端计算密集的完整谱系**。

| Benchmark | CCR | 角色 | 设计逻辑 |
|-----------|:--:|------|---------|
| Optic | 0.06 | 极端通信密集 | 16 PE→4 GB 全并发回传，1μs 计算 + 32KB 数据，模拟 GPU DMA 或 all-to-all 集合通信 |
| VOPD | 0.3 | 通信为主 | 13 tasks pipeline，7-10μs 计算 + 6-94KB 数据，代表典型视频处理负载 |
| MPEG4 | 1 | 转折点 | 12 tasks，10-25μs 计算 + 4-62.5KB 数据，定位 CCR≈1 的过渡区 |
| HNN | 3 | 计算倾向 | 32 tasks 深度流水线，20-50μs 计算 + 8-32KB，代表神经网络推理 |
| GEMM | 8 | 极端计算密集 | 11 tasks 矩阵乘归约树，15-50μs 计算 + 1-8KB，代表 HPC 计算核 |

**CCR 取值的关键约束**：CCR 不能取任意值，因为 `computeTime` 和 `dataSize` 也决定仿真时长和 flit 数量：
- 计算时间不能太短（<1μs）——PE 来不及升温，热效应无法观察
- 计算时间不能太长（>100μs）——仿真事件爆炸，OMNeT++ 无法在合理时间内完成
- 数据量不能太小（<1KB）——光电路 setup 开销（~100ns）无法摊平
- 数据量不能太大（>100KB）——波长占用时间过长，阻塞后续电路

这五个 benchmark 的 `computeTime` 和 `dataSize` 均在上述可行范围内。

#### 7.10.3 文献中的"盈亏平衡点"佐证

混合光电 NoC 文献中普遍存在 **break-even message size**（盈亏平衡消息大小）概念：

- **Beux et al. (DATE 2015)**：光旁路仅在消息 > ~50 flits 时才有收益，因为 SETUP_REQ/ACK 握手 ~100ns 开销需要被高带宽传输摊平
- **Gu et al. (MRONoC, 2017)**：微环光 NoC 的盈亏平衡点为 ~100-200 flits（~1.6-3.2KB @ 16B/flit）
- **Koohi et al. (2011)**：电路交换光 NoC 的最小有益消息大小 ~1KB

本文的 CCR 框架将"消息大小阈值"概念推广为 **CCR 阈值**：
- 盈亏平衡 flit 数 × 8ns/flit = 盈亏平衡通信时间
- 当 computeTime / (盈亏平衡 flit × 8ns) ≈ 1 时，光电混合 NoC 从"有益"转变为"无益"
- 本文实验将此阈值定位在 CCR ≈ 1 附近（MPEG4: 时间优势 1.87× 但能耗略增）

#### 7.10.4 关于"可调性"的防御策略

**可能的审稿质疑**："你调整了数据包大小和计算时间，CCR 是你人为设定的，结论不可靠。"

**防御论据**：

1. **CCR 梯度而非绝对值是本文贡献**。我们证明的是"CCR 越低，光层收益越大"这一**单调关系**，而非某个特定 CCR 值的收益。即使将 MPEG4 的 CCR 从 1 调到 1.5，结论"CCR>1 时光层无能耗优势"仍然成立。

2. **7.10 节（原 7.10，现 7.11）的数据翻倍实验证明了鲁棒性**。数据量翻倍（CCR 减半）后：
   - 光层收益的**排名不变**（Optic > VOPD > MPEG4 > HNN > GEMM）
   - 光/电收发器比**不变**（恒为 1:7.5）
   - 仅具体数值变化，定性结论完全保留

3. **Benchmark 选择有文献依据**。VOPD、MPEG4、GEMM 是 NoC 映射研究中最常用的 benchmark（出现在 100+ 篇 NoC 论文中）。Optic 和 HNN 虽为自定义，但代表了真实负载类别（批量数据传输和神经网络推理）。

4. **我们未声称这些 CCR 值是 VOPD/MPEG4/HNN/GEMM 的"标准值"**。论文中应明确："本文通过调整 dataSize 和 computeTime，使 benchmark 覆盖 CCR=0.06 至 CCR=8 的谱系，以系统评估光层在不同计算/通信比下的表现。"

#### 7.10.5 建议的论文表述

> "The five benchmarks are intentionally configured to span CCR from 0.06 (extreme communication-bound) to 8 (extreme compute-bound), forming a systematic gradient for evaluating the hybrid photonic-electronic NoC. While the specific CCR values are implementation-dependent and not claimed as inherent properties of these benchmarks, the monotonic relationship we demonstrate—that optical benefit decreases with increasing CCR—is robust to parameter variations, as verified by our 2× data scaling experiments (Section 7.11). The choice of benchmarks is motivated by their widespread use in NoC mapping literature: VOPD and MPEG4 represent multimedia workloads, GEMM represents HPC kernels, HNN represents neural network inference, and Optic represents bulk data transfer."

## 十一、论文结论

1. **CCR 是决定光电混合 NoC 收益的核心指标**。通信密集场景（CCR<1）下光层在时间和能耗两个维度均显著优于纯电；计算主导场景（CCR>3）下光层无明显优势。该结论与文献中光 NoC 存在"盈亏平衡消息大小"的共识一致——光旁路仅在该阈值以上才有收益（Beux et al.; Gu et al., MRONoC, 2017）。

2. **微环热调谐功耗是光层主要开销，动态按需调谐可大幅降低**。全芯片 2560 个微环在最坏情况下的基线热调谐功耗可达 5.12W。2026-05-31 实现了动态按需调谐，2026-06-01 修正了 NI 调制/解调器微环计数模型（共享链 ring 1..maxWl，消除 per-λ 重复计数）。实测动态调谐平均功率极低（< 3 mW），TuningRatio < 0.13%。该方案将调谐功耗从"通信无关的固定开销"转变为"与通信负载成比例的可变开销"，验证了按需调谐策略的有效性。

3. **光电路建立开销（~100ns）限制了对小数据包的应用**。仅当单次传输数据量足够大（>100 flits）时，256Gbps 光带宽优势才能摊平 setup 成本。

4. **光电混合架构应设计为按需选择性启用光旁路**。对于通信密集段，启用光旁路以获取带宽优势；对于计算主导段，使用纯电路由以避免光器件静态功耗。这比"全面光化"或"全面电化"都更务实。
