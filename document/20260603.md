## 一、系统概述

### 1.1 架构总览

**Task-driven 光电混合片上网络仿真器**。4×4 Mesh拓扑，16个TaskPE + 16个5端口光路由器 + 1个GlobalBuffer。

控制面走电路由器（电层握手），数据面走光波导（sendDirect直传）。每条光电路先经SETUP_REQ→SETUP_ACK电层握手分配波长，再通过光旁路直传全部数据flits，END_FLIT触发拆链和波长释放。

```
控制面（电）:  setup_req → 电 router → setup_ack
数据面（光）:  START_FLIT → sendDirect → ... → END_FLIT → teardown
热调谐（基线）: 160 微环/路由器 × 2mW/环 → 320mW/路由器 → 全芯片最坏 5.12W
SOA（逐跳）:   每路由器输出端口后 SOA × 80mW/器件 → 按电路持续时间累计能耗
激光器（片外）: CW 常亮, P_elec = 1mW / 0.20 = 5mW, 不计入芯片热模型
```

### 1.2 关键设计决策

- **电层基线保守化**：PE功耗、热阻参数取成熟CMOS工艺保守值（非先进节点），确保与光层的对比区分度
- **光层参数物理一致性**：C++与Python器件参数统一对齐，SOA增益下调至10 dB避免逐跳过饱和，接收灵敏度上调至-12 dBm符合256G PAM4现实值
- **周期性DVFS**：每100ns重检PE温度并调整计算推进速率，替代原一次性DVFS方案
- **CCR谱系Benchmark**：5个任务图覆盖CCR 0.06→8全范围，系统评估光层在不同计算/通信比下的收益

## 三、光路由器微环架构

5端口microring-based光路由器。端口定义：**0=Local, 1=West, 2=North, 3=East, 4=South**。

物理实现为waveguide crossing交叉杆拓扑：5×5交叉点，排除5个自路由对角，有效交叉点20个。每个交叉点串联8个微环谐振器（每WDM波长一个）。

> **20交叉点 × 8波长 = 160微环/路由器。全芯片16 × 160 = 2560个微环。**

各方向路径的through-count公式（n=8波长, i为波长索引1..8），每路径额外dropCount=1：

| 方向组 | 公式类型 | through范围 | 最长 (i=8) |
|--------|:---:|------|:---:|
| L→W, W→S, N→L, E→N | Type 0: i−1 | 0–7 | 8 |
| L→S, N→W, E→L, S→E | Type 1: 2n+i−1 | 16–23 | 24 |
| L→N, L→E, W→L, S→L | Type 2: 3n+i−1 | 24–31 | 32 |
| W→E, N→S, E→W, S→N | Type 3: 4n | 32 | 33 |
| W→N, E→S | Type 4: 4n+i−1 | 32–39 | 40 |
| N→E, S→W | Type 5: 6n+i−1 | 48–55 | **56** |

### 4.3 光传输时序

```
Task计算完成
  → sendTaskData(): 创建全部flits, 放入pendingDataQ[dst]
  → tryReserveSetupPath(): XY路径预留2个波长
  → 电层路由发送SETUP_REQ
  → 等待SETUP_ACK (超时200ns, 重试间隔50ns)

SETUP_ACK到达
  → circuitReadyByDst[dst] = 1
  → flushPendingData(): 全部flits → opticalDataQ
  → sendOpticalFlitFromQ(): 逐个flit sendDirect (START → ... → END)

END_FLIT发出
  → releaseOpticalPathByToken() 释放波长
  → SOA电能耗累计: soaCount × 80mW × 持续时间
  → 动态调谐能耗累计: 移除各路由器热调谐功率, 累计Σ tuningPower × duration
  → circuitReadyByDst[dst] = 0
```

**光层每flit传输时间**: 16B × 8 / 256Gbps = **0.5 ns**
**电层每flit传输时间**: 16B × 8 / 16Gbps = **8 ns**

### 4.4 Per-Router独立调谐计算

各路由器独立查询自身温度，直接计算自己的调谐功率：

```
for each router i on the path:
    1. 从pathEdges推导(dx, dy) → 方向端口映射
    2. 查routerTurnMatrices[inPort][outPort] → formulaType → throughCount
    3. ringCount_i = throughCount + numActiveWL (路由器转向)
       if (i == 0) ringCount_i += maxWl (源NI调制器共享链)
       if (i == numRouters-1) ringCount_i += maxWl (目的NI解调器共享链)
    4. P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
```

> NI调制器/解调器的微环数为`maxWl`（ring 1..maxWl共享链），非`numActiveWL`。

### 4.5 SOA功率精确归属

每个SOA位于前一跳路由器的输出端，功率归属到驱动路由器：
- routers[0..N-2]各得80mW
- routers[N-1] (dstId) = 0

## 五、波长分配

### 5.1 分配流程

1. `buildXYPathEdges()` — 构建XY维序路由边列表
2. 遍历2个spatial channel，对每个channel收集所有空闲波长
3. 策略`"lowest"`: 取前`opticalRequiredWavelengths`(2)个最低索引空闲波长
4. 占用: `edgeOccupancy[spatial][wlIdx] = pktId`
5. 预计算设备级光链路预算并缓存
6. 若所有spatial channel均不足 → 返回失败，PE进入重试循环

### 5.2 边容量

```
每边槽位 = 8λ × 2 spatial = 16
每电路占用 = 2λ
每边最大并发 = 8条电路
```

## 六、CCR与Benchmark设计

### 6.1 CCR定义

**CCR (Compute-to-Communication Ratio)** 衡量任务的计算密集度：

```
CCR = computeTime_ns / (numFlits × 8 ns)
```

- CCR < 1：通信主导，光层256Gbps带宽优势显著
- CCR ≈ 1：平衡，光层有加速但需考虑能耗代价
- CCR > 1：计算主导，传输时间被计算掩埋

### 7.8 关键发现

1. **CCR < 1（Optic、VOPD）：光层完胜**。时间缩短4-6×，能耗降低49-59%。
2. **CCR ≈ 1（MPEG4）：转折点/接近盈亏平衡**。时间缩短1.87×，光层总能耗仅比电层高2.3%。
3. **CCR > 3（HNN、GEMM）：光层得不偿失**。时间几乎无差（1.14-1.34×），总能耗反超18-35%。
4. **Ring tuning是光层能耗的主要挑战**：动态按需调谐将调谐功耗从"通信无关的固定开销"转变为"与通信负载成比例的可变开销"。
5. **CCR是预测光层收益的可靠指标**：存在"盈亏平衡消息大小"，CCR将该直觉量化为可计算指标。
6. **稳态ΔT的主要来源是PE计算功耗通过R_pe2router热耦合加热路由器**，调谐功耗是温度变化的"消费者"而非"生产者"。

### 7.9 数据量翻倍鲁棒性验证

数据量翻倍后：光层收益的排名不变（Optic > VOPD > MPEG4 > HNN > GEMM），光/电收发器比不变（恒为1:7.5），仅具体数值变化，定性结论完全保留。

### 7.10 CCR严谨性说明

CCR不是benchmark的固有属性——同一benchmark不同实现者会得到完全不同的CCR。本文策略是以CCR为自变量覆盖完整谱系。CCR取值受仿真可行性约束（计算时间不能太短/太长，数据量不能太小/太大）。本文证明的是"CCR越低，光层收益越大"这一单调关系，而非某个特定CCR值的收益。

## 九、论文结论

1. **CCR是决定光电混合NoC收益的核心指标**。通信密集场景（CCR<1）下光层在时间和能耗两个维度均显著优于纯电；计算主导场景（CCR>3）下光层无明显优势。

2. **微环热调谐功耗是光层主要开销，动态按需调谐可大幅降低**。全芯片2560个微环最坏情况基线热调谐功耗5.12W。动态按需调谐将调谐功耗从"通信无关的固定开销"转变为"与通信负载成比例的可变开销"，实测TuningRatio<0.05%，即使在稳态热点下也能将调谐功耗控制在1-2W以内（节省4-200×）。

3. **光电路建立开销（~100ns）限制了对小数据包的应用**。仅当单次传输数据量足够大（>100 flits）时，256Gbps光带宽优势才能摊平setup成本。

4. **光电混合架构应设计为按需选择性启用光旁路**。对于通信密集段启用光旁路以获取带宽优势；对于计算主导段使用纯电路由以避免光器件静态功耗。

5. **SOA而非微环调谐是光层动态功耗的主导**。SOA逐跳放大功耗（80 mW/跳×活跃跳数）在所有benchmark中均超过调谐功耗1-3个数量级，是光层动态功耗的首要优化目标。

6. **仿真时间尺度是根本局限**。10-205 μs不足以让芯片达到热稳态。当前结果代表"冷启动"瞬态行为，建议在论文中增加稳态分析或解析模型投影。

## 十、后续方向：热感知任务映射

### 10.1 公共基础设施：Python热仿真器

方向B-1、B-2、C共同依赖一个与OMNeT++解耦的Python热仿真器（`mapping/thermal_simulator.py`），精确复现OMNeT++的RC热模型（显式欧拉法，32节点，100ns步长）。包含三个组件：

| 组件 | 功能 |
|------|------|
| **TaskScheduler** | DAG感知事件驱动调度，PE串行化，通信延迟建模 |
| **PowerModel** | 计算/空闲功耗追踪 + DVFS热降频（T > 46.85°C → 5%/°C减速） |
| **ThermalSimulator** | RC热网络求解器，逐时间步记录所有PE的完整温度曲线 |

优化在Python内完成（毫秒级/轮），OMNeT++仅用于最终验证（跑一次）。

### 10.2 方向定位总览

| | 方向B-1（增量贪心+迭代） | 方向B-2（GA） | 方向C（GNN+RL） |
|---|---|---|---|
| **调度时机** | 设计时（t=0） | 设计时（t=0） | 设计时（t=0）+ 可扩展在线 |
| **决策方式** | 贪心规则 + 实时热注入 | 种群进化 + 完整仿真 | GCN编码 + RL策略网络 |
| **方法类型** | 解析方法（规则驱动） | 元启发式搜索 | 深度学习 |
| **论文定位** | Baseline | Baseline | **Proposed**（算法创新） |
| **自洽性** | ✅ 每步注入热效应 | ✅ 每个体独立仿真 | ✅ 训练环境提供真实代价 |
| **全局搜索** | ❌（靠多轮弥补） | ✅ 种群多样性 | ✅ RL探索策略 |
| **可泛化到新benchmark** | ❌（需重跑） | ❌（需重跑） | ✅ 训练一次直接推理 |
| **实现工作量** | 低 | 中 | 高（PyTorch + 热仿真器） |

### 10.3 方向B-1：增量贪心+多轮迭代

**核心思想**：按DAG拓扑序逐个分配task，每分配完一个task就立刻跑热仿真把它的热效应注入进去——下一个task评估PE时看到的是"前面所有task已经烧热了的芯片"。单轮贪心不能回溯（T1选错→后面全错），用多轮迭代弥补。

```
单轮内部（增量贪心构建）:
  T=0，所有PE=45°C
  分配T1 → 选代价最低的PE → 跑热仿真到T1结束 → PE温度更新
  分配T2 → 候选PE有不同的实时温度 → 选PE_j → 跑热仿真注入T2的热
  分配T3 → 芯片已经被T1、T2加热 → 看到真实的温度梯度 → 选PE_k
  ...直到所有task分配完毕
  → 产出映射A + 完整温度时间曲线

轮间迭代:
  Round 1: 贪心构建（无历史经验，初始分配近似随机）
  Round 2: 贪心构建（用Round 1的温度经验重选，纠正Round 1的错误）
  Round 3: ...直到映射不再变化
```

**代价函数**：

$$\text{cost}(PE_j, task_i) = w_T \cdot (T_{PE_j}(t_{start}) - T_{amb}) + w_H \cdot \sum_{p \in pred(i)} \text{hops}(PE_{p}, PE_j) \cdot \text{dataSize}(p,i)$$

其中$T_{PE_j}(t_{start})$是task_i开始时刻PE_j的真实温度（来自已注入热效应的当前热状态）。

| 优点 | 缺点 |
|------|------|
| 每一步的评估完全自洽 | 单轮贪心无回溯能力 |
| 概念直观，实现简单 | 需要多轮才能收敛 |
| 热状态是连续时间函数，精度最高 | 最终结果可能不如全局优化 |

### 10.4 方向B-2：遗传算法（GA）

**核心思想**：每个"个体"是一个完整映射（所有task→PE的分配）。评估个体 = 用Python热仿真器跑一次该映射的完整仿真 → 得到真实温度分布 → 计算真实代价。种群通过选择、交叉、变异迭代进化。

```
GA流程:
  初始化: 随机生成50个完整映射（个体）
  每代:
    对每个个体跑Python热仿真 → 真实温度 + 真实代价
    选择: 保留代价最低的20个
    交叉: 两个父代交换部分task的PE分配 → 新个体
    变异: 随机修改一个task的PE
    → 新一代50个个体
  20-30代后收敛 → 最优映射
```

**染色体编码**：`[PE_T1, PE_T2, PE_T3, ..., PE_Tn]`

**并行化**：50个体×20代=1000次仿真。每次仿真~0.05s。单线程~50秒，8线程并行~6秒。

| 优点 | 缺点 |
|------|------|
| 每个评估完全自洽（映射→仿真→温度→代价，闭环） | 仿真次数多（但可并行） |
| 种群多样性防止局部最优 | 实现比B-1复杂 |
| 可输出帕累托前沿（温度最优vs通信最优的多个解） | 超参调优（种群大小、交叉率、变异率） |

### 10.5 方向C：GNN+RL智能映射

**核心思想**：将task graph和mesh拓扑视为两个图，用图神经网络（GNN）联合编码，强化学习（RL）学习最优PE分配策略。与方向B的关键区别：B-1/B-2对每个新benchmark都需要重新搜索；方向C训练一次后，换一个新的task graph可直接推理输出映射。

```
训练阶段（Python内完成）:
  GNN输入task graph → 输出映射
    ↓
  Python热仿真器跑该映射 → 得到真实温度 + 通信代价
    ↓
  reward = -(w_H × 通信代价 + w_T × 温度代价)
    ↓
  PPO更新策略网络
    ↓
  下一个task graph...

推理阶段:
  新task graph → GNN → 映射 → OMNeT++验证一次
```

**参考论文RA-Map (2024)**：GCN编码器+局部注意力机制+RL策略网络用于3D NoC任务映射，通信成本比DPSO降6.5%、比SA降8.5%。

**我们的差异化**：RA-Map的代价函数只有通信成本。我们的创新是将温度项融入reward，用Python热仿真器作为RL训练环境，实现通信+温度联合优化。

**为什么GNN天然适合这个任务**：

| 数据 | 天然图结构 | GNN能做什么 |
|------|-----------|-------------|
| Task graph | 有向无环图（节点=task，边=依赖+通信量） | GCN聚合邻居节点信息，学习task间的通信模式 |
| 4×4 Mesh | 网格图（节点=PE，边=NoC链路） | 编码PE的拓扑位置和相邻关系 |
| 温度分布 | 每个PE一个标量 | 作为PE节点的额外特征，GCN自然处理 |

**实现路线图**：
- Phase 1（基础复现）：PyTorch Geometric实现GCN编码器+PPO RL策略网络，复现RA-Map通信成本结果
- Phase 2（温度项融入）：将Python热仿真器包装为RL环境，reward加入温度代价
- Phase 3（在线/离线混合）：初始映射用训练好的GNN模型t=0一次性分配，运行时若检测到局部热点触发局部重映射

| 优点 | 缺点 |
|------|------|
| **最前沿**：GNN+RL是2024-2025最热门组合 | 实现复杂度高于B-1/B-2 |
| **可泛化**：训练一次可用不同task graph | 需要大量训练数据（可从Python热仿真器生成） |
| **论文故事强**：复现+创新（温度项）+对比充分 | PyTorch/OMNeT++跨框架集成有工程挑战（已解耦） |

### 10.6 建议的论文实验设计

1. **Baseline 1**：传统XY路由 + 固定映射（当前`tasks_*_static.csv`）
2. **Baseline 2**：方向B-1增量贪心+多轮迭代（解析方法）
3. **Baseline 3**：方向B-2 GA优化（元启发式方法）
4. **Proposed A**：传统XY路由 + 方向A运行时热感知动态放置（控制数据分离）
5. **Proposed C**：方向C GNN+RL智能映射 — 离线训练、在线推理，通信+温度联合代价

对比维度：温度（峰值/梯度）、通信代价（总跳数×数据量）、完成时间、能耗。

### 11.4 关键验证结论

- **零reserve-fail跨所有benchmark**：波长池(8λ×2spatial=16槽)在2λ/电路配置下充足
- **Timeout存在但全部恢复**：所有timeout后重试成功，电路建立率100%
- **Stale ACK极少**：最高GEMM 12个，仅当ACK在timeout清除pending状态后到达
- **能量闭合精确**：PE的totalEnergyJ = totalStaticEnergyJ + totalDynamicEnergyJ（浮点精度极限）
- **DVFS节流仅在HNN/GEMM触发**：HNN所有16 PE均超温（节流比8.2-14.4%），GEMM 16 PE均节流（3.4-5.9%）
- **波长管理无泄漏**：VOPD/MPEG4/HNN/GEMM在finish时occupied-slots=0
