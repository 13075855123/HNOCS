> 最后更新: 2026-05-31

## 一、系统概述

### 1.1 架构总览

**Task-driven 光电混合片上网络仿真器**。4×4 Mesh 拓扑，16 个 TaskPE + 16 个 5 端口光路由器 + 1 个 GlobalBuffer。

控制面走电路由器（电层握手），数据面走光波导（sendDirect 直传）。每条光电路先经 SETUP_REQ→SETUP_ACK 电层握手分配波长，再通过光旁路直传全部数据 flits，END_FLIT 触发拆链和波长释放。

```
控制面（电）:  setup_req → 电 router → setup_ack
数据面（光）:  START_FLIT → sendDirect → ... → END_FLIT → teardown
热调谐（基线）: 160 微环/路由器 × 2mW/环 → 320mW/路由器 → 全芯片最坏 5.12W
SOA（逐跳）:   每路由器输出端口后 SOA × 80mW/器件 → 按电路持续时间累计能耗
激光器（片外）: CW 常亮, P_elec = 1mW / 0.20 = 5mW, 不计入芯片热模型
```

### 1.2 关键设计决策

- **电层基线保守化**：PE 功耗、热阻参数取成熟 CMOS 工艺保守值（非先进节点），确保与光层的对比区分度
- **光层参数物理一致性**：C++ 与 Python 器件参数统一对齐，SOA 增益下调至 10 dB 避免逐跳过饱和，接收灵敏度上调至 -12 dBm 符合 256G PAM4 现实值
- **周期性 DVFS**：每 100ns 重检 PE 温度并调整计算推进速率，替代原一次性 DVFS 方案
- **CCR 谱系 Benchmark**：5 个任务图覆盖 CCR 0.06→8 全范围，系统评估光层在不同计算/通信比下的收益

## 三、光路由器微环架构

5 端口 microring-based 光路由器。端口定义：**0=Local, 1=West, 2=North, 3=East, 4=South**。

物理实现为 waveguide crossing 交叉杆拓扑：5×5 交叉点，排除 5 个自路由对角，**有效交叉点 20 个**。每个交叉点串联 8 个微环谐振器（每 WDM 波长一个）。

> **20 交叉点 × 8 波长 = 160 微环/路由器。全芯片 16 × 160 = 2560 个微环。**

各方向路径的 through-count 公式（n=8 波长, i 为波长索引 1..8），每路径额外 dropCount=1：

| 方向组 | 公式类型 | through 范围 | 最长 (i=8) |
|--------|:---:|------|:---:|
| L→W, W→S, N→L, E→N | Type 0: i−1 | 0–7 | 8 |
| L→S, N→W, E→L, S→E | Type 1: 2n+i−1 | 16–23 | 24 |
| L→N, L→E, W→L, S→L | Type 2: 3n+i−1 | 24–31 | 32 |
| W→E, N→S, E→W, S→N | Type 3: 4n | 32 | 33 |
| W→N, E→S | Type 4: 4n+i−1 | 32–39 | 40 |
| N→E, S→W | Type 5: 6n+i−1 | 48–55 | **56** |

### 4.3 光传输时序

```
Task 计算完成
  → sendTaskData(): 创建全部 flits, 放入 pendingDataQ[dst]
  → tryReserveSetupPath(): XY 路径预留 2 个波长
  → 电层路由发送 SETUP_REQ
  → 等待 SETUP_ACK (超时 200ns, 重试间隔 50ns)

SETUP_ACK 到达
  → circuitReadyByDst[dst] = 1
  → flushPendingData(): 全部 flits → opticalDataQ
  → sendOpticalFlitFromQ(): 逐个 flit sendDirect (START → ... → END)

END_FLIT 发出
  → releaseOpticalPathByToken() 释放波长
  → SOA 电能耗累计: soaCount × 80mW × 持续时间
  → 动态调谐能耗累计: 移除各路由器热调谐功率, 累计 Σ tuningPower × duration
  → circuitReadyByDst[dst] = 0
```

**动态热调谐时序**:
```
SETUP_ACK 到达
  → getDeviceLevelPathMetrics() 构建全路径器件链
  → 各路由器独立计算调谐功率（不依赖 budget 汇总值）:
      从 pathEdges 推导每跳 (dx,dy) → 端口映射 → 查 routerTurnMatrices
        → formulaType → throughCount = evalFormula(maxWl, totalWL)
        → ringCount_i = throughCount + numActiveWL (路由器转向)
        → 源 NI: ringCount_i += numActiveWL (调制器)
        → 目的 NI: ringCount_i += numActiveWL (解调器)
      P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
  → addRouterOpticalPower(routerId, P_i) 注入热模型
  → SOA 功率: 每跳前一个路由器出端有一个 SOA
      → routers[0..N-2] 各得 opticalSoaPumpPower_mW (dstId 无 SOA)

END_FLIT 发出
  → removeRouterOpticalPower() 逐路由器移除
  → totalDynamicTuningEnergy_J += Σ tuningPower × circuitDuration
  → totalSoaEnergy_J += soaCount × 80mW × circuitDuration
```

**光层每 flit 传输时间**: 16B × 8 / 256Gbps = **0.5 ns**
**电层每 flit 传输时间**: 16B × 8 / 16Gbps = **8 ns**

### 4.4 预算模型路径构建修复 (2026-05-30)

端口映射修正为统一逻辑约定 (0=Local, 1=West, 2=North, 3=East, 4=South)。修复内容包括:

| 问题 | 修复前 | 修复后 |
|------|--------|--------|
| 南向 (dy=+1) 端口 | N→L (inP=2, outP=0) | N→S (inP=2, outP=4) |
| 北向 (dy=-1) 端口 | L→N (inP=0, outP=2) | S→N (inP=4, outP=2) |
| 目的路由器转向 | **缺失** | 新增 direction→Local(0) egress turn |
| deviceIndex 编码 | 不一致 | 统一 `nodeId×1000 + inPort×100 + outPort×10 + subIdx` |

2026-05-31 验证结果：10/10 单元测试通过，覆盖 4 方向 × 3 角色端口映射、20 port pair 合法性、单跳/自环边界、SNR=38.6dB 预算合理性、deviceIndex 编码一致性。

### 4.5 Per-Router 独立调谐计算 (2026-05-31)

旧方案：budget 函数计算 `totalTuningPower_mW`，随后在 `tryAllocateOpticalPathForPacket` 中按各路由器 ΔT 比例分配 → 近似值，与底层逐环计算不完全一致。

新方案：**各路由器独立查询自身温度，直接计算自己的调谐功率**，不依赖 budget 的汇总值。

```
for each router i on the path:
    1. 从 pathEdges 推导 (dx, dy) → 方向端口映射:
       - 源路由器: inPort=0(Core), outPort=direction
       - 中间路由器: inPort=来向反方向, outPort=去向
       - 目的路由器: inPort=来向反方向, outPort=0(Core)

    2. 查 routerTurnMatrices[inPort][outPort] → formulaType → throughCount:
       - Type 0: maxWl-1
       - Type 1: 2n + maxWl - 1
       - Type 2: 3n + maxWl - 1
       - Type 3: 4n
       - Type 4: 4n + maxWl - 1
       - Type 5: 6n + maxWl - 1

    3. ringCount_i = throughCount + numActiveWL           (路由器转向)
       if (i == 0) ringCount_i += numActiveWL              (源 NI 调制器)
       if (i == numRouters-1) ringCount_i += numActiveWL   (目的 NI 解调器)

    4. P_i = ringCount_i × 0.5 mW/nm × 0.10 nm/K × |T_i − 318.15K|
```

### 4.6 SOA 功率精确归属 (2026-05-31)

旧方案：SOA 总功率均摊到路径所有路由器（含 dstId）→ 物理不准确。

新方案：每个 SOA 位于前一跳路由器的输出端，功率归属到驱动路由器。

```
SOA 归属: routers[0..N-2] 各得 opticalSoaPumpPower_mW (80mW)
          routers[N-1] (dstId) = 0  (不驱动任何输出)
总 SOA 功率: 80mW × pathEdges.size() (不变)
```

## 五、波长分配

### 5.1 分配流程

1. `buildXYPathEdges()` — 构建 XY 维序路由边列表
2. 遍历 2 个 spatial channel，对每个 channel 收集所有空闲波长
3. 策略 `"lowest"`: 取前 `opticalRequiredWavelengths` (2) 个最低索引空闲波长
4. 占用: `edgeOccupancy[spatial][wlIdx] = pktId`
5. 预计算设备级光链路预算并缓存
6. 若所有 spatial channel 均不足 → 返回失败，PE 进入重试循环

### 5.2 数据结构

```
opticalEdgeOccupancy: map<edgeKey, [numSpatialChannels][maxWavelengths]>
  — 每条无向边的 (spatial, wavelength) 占用矩阵

opticalPacketAllocations: map<pktId, OpticalPacketAllocation>
  — 每条活跃光路的完整信息, 含:
      pathRouters, tuningPowerPerRouter_mW(vector), soaPowerPerRouter_mW(vector),
      setupTime (用于 SOA 能耗 + 动态调谐能耗计算)

OpticalDevicePath::perRouterTuningPower_mW: map<routerId, power_mW>
  — computeDeviceLevelBudget 按 deviceIndex/1000 分组累加
  — 可用于与 per-router 独立计算交叉验证
  — 通过 OpticalPathMetrics::perRouterTuningPower_mW 对外暴露
```

### 5.3 边容量

```
每边槽位 = 8λ × 2 spatial = 16
每电路占用 = 2λ
每边最大并发 = 8 条电路
```

## 六、CCR 与 Benchmark 设计

### 6.1 CCR 定义

**CCR (Compute-to-Communication Ratio)** 衡量任务的计算密集度：

```
CCR = computeTime_ns / (numFlits × 8 ns)
```

- CCR < 1：通信主导，光层 256Gbps 带宽优势显著
- CCR ≈ 1：平衡，光层有加速但需考虑能耗代价
- CCR > 1：计算主导，传输时间被计算掩埋

### 6.2 五个 Benchmark 设计

设计原则：形成 CCR 从 0.06 到 8 的谱系，系统评估光层在不同工作负载下的表现。

| Benchmark | 角色 | 目标 CCR | 计算 (ns) | 数据量 (B) | 最大 flits |
|---|---|---|---|---|---|
| **Optic** | 极端通信密集 | ~0.06 | 1,000 | 4K–32K | 2,048 |
| **VOPD** | 通信为主 | ~0.3 | 7K–10K | 6K–96K | 6,000 |
| **MPEG4** | 平衡型 | ~1 | 10K–25K | 4K–64K | 4,000 |
| **HNN** | 计算倾向 | ~3 | 20K–50K | 8K–32K | 2,048 |
| **GEMM** | 极端计算密集 | ~8 | 15K–50K | 1K–8K | 512 |

**Optic**: 16 PE→4 GB 端口，全并发回传，通信压力最大。
**VOPD**: 13 tasks pipeline，大数据级间传递。
**MPEG4**: 12 tasks，中等计算和通信混合。
**HNN**: 32 tasks 深度 4 级流水线，16 PE 并行 Stage 3，重度计算。
**GEMM**: 11 tasks 矩阵乘归约树，计算 dominate。

### 7.5 关键发现

1. **CCR < 1（Optic、VOPD）：光层完胜**。时间缩短 4-6×，能耗降低 47-59%。大数据量摊平光电路 setup 开销，256Gbps vs 16Gbps 带宽优势主导。

2. **CCR ≈ 1（MPEG4）：转折点**。时间缩短 1.87×，但 Ring tuning 常开功耗（占光层总能耗 34%）导致总能耗略高于电层（+6.8%）。"时间赚了，能耗亏了"。

3. **CCR > 3（HNN、GEMM）：光层得不偿失**。时间几乎无差（1.05-1.19×），因为计算主导了总延迟。Ring tuning 能耗是纯负担，总能耗反超 33-48%。

4. **Ring tuning 是光层能耗的主要挑战**：全芯片 2560 个微环在最坏情况（全部需要热锁定）下总基线功耗达 5.12W。文献中 Padmaraju & Bergman (2014) 指出"热调谐是微环光链路的主要功耗来源"。实际应用中可通过仅锁定活跃环、动态电源门控等方式降低开销。在本仿真中虽因仿真时间短（μs 级）绝对能耗不大，但占比已很显著（Optic 31%、MPEG4 34%）。

5. **CCR 是预测光层收益的可靠指标**：文献中光 NoC 研究的共识是存在"盈亏平衡消息大小"（break-even message size）——消息必须足够大才能摊平电路建立开销（Beux et al., *Path-Setup Architecture for Hybrid Photonic-Electronic NoCs*; Gu et al., *MRONoC*, 2017）。CCR 将该直觉量化为可计算指标，使论文可用 CCR 梯度论证"光电混合 NoC 应依据工作负载的通信密集度来决定是否启用光旁路"。

### 7.6 Optic 拥塞分析（附注）

初始参数设置中误将 `opticalRequiredWavelengths=8`，导致 16 PE 回传 GB 时共享边 R1→R0 需要 24 槽（3PE×8λ）但只有 16 槽（8λ×2spatial），波长分配死锁，仿真跑满 20ms 产生 3.59 亿事件。修正为 2λ/电路后问题消失，所有 16 PE 正常完成。

## 十一、论文结论

1. **CCR 是决定光电混合 NoC 收益的核心指标**。通信密集场景（CCR<1）下光层在时间和能耗两个维度均显著优于纯电；计算主导场景（CCR>3）下光层无明显优势。该结论与文献中光 NoC 存在"盈亏平衡消息大小"的共识一致——光旁路仅在该阈值以上才有收益（Beux et al.; Gu et al., MRONoC, 2017）。

2. **微环热调谐功耗是光层主要开销，动态按需调谐可大幅降低**。全芯片 2560 个微环在最坏情况下的基线热调谐功耗可达 5.12W。2026-05-31 实现了动态按需调谐：仅活跃电路中经过的微环才进行热补偿，调谐功率由 `computeDeviceLevelBudget` 逐个微环按所在路由器温度实时计算（热光系数 0.10 nm/K, 调谐效率 0.5 mW/nm），随电路建立注入热模型、随电路拆除移除。MPEG4 基准测试中动态调谐平均功率仅 2.06 mW，为静态最坏基线的 0.04%。该方案将调谐功耗从"通信无关的固定开销"转变为"与通信负载成比例的可变开销"，验证了按需调谐策略的有效性。

3. **光电路建立开销（~100ns）限制了对小数据包的应用**。仅当单次传输数据量足够大（>100 flits）时，256Gbps 光带宽优势才能摊平 setup 成本。该开销与文献中的分析一致（Koohi et al., 2011; Pasricha et al., 2014）。

4. **光电混合架构应设计为按需选择性启用光旁路**。对于通信密集段，启用光旁路以获取带宽优势；对于计算主导段，使用纯电路由以避免光器件静态功耗。这比"全面光化"或"全面电化"都更务实——与文献中分层混合 NoC（Hierarchical Hybrid NoC）的设计理念一致。
